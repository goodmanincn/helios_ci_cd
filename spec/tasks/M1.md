### T1.2.2 Webhook 接收端点 (1d)  ✅ 2026-06-10
**描述**: 接收 GitHub push 事件
**步骤**:
- POST /webhooks/github/:project_id
- HMAC-SHA256 签名校验 (X-Hub-Signature-256)
- 解析 push event (branch / commits / pusher)
- 过滤分支 (按项目配置)
- 入队 Asynq 任务 (run.create)
- 返回 202

**验收**: GitHub 模拟器发 push event,DB 出现 run 记录,状态 pending

**完成产物** (2026-06-10):
- `api/internal/handler/webhook/github.go` (330 行) — 整套流水线:
  1. 解析 project_id + X-GitHub-Event header
  2. ping 直接 200/pong
  3. store.GetProject (校验存在 + repo_type=github)
  4. 读 body (io.LimitReader 10MB cap 防 OOM)
  5. 校验 X-Hub-Signature-256 (resolveSecret: project.config.webhook_secret 优先,devSecret 兜底)
  6. 非 push event 静默 202
  7. ParsePushEvent → 非分支(tag)静默,非默认分支静默,默认分支才落 run
  8. **未入队 Asynq** — MVP 阶段直接同步写 runs(status=pending),T1.3.2 引擎接管后再加 Asynq dispatch
- `RunStore` 接口 + `GormRunStore` 实现 — 抽接口便于单元测试 (handler 完全不依赖 *gorm.DB)
- `GormRunStore.CreateRunForPush` 单事务里:拿/建 default pipeline → 拿/建 v1 pipeline_version(spec 占位 `{"stages":[]}`)→ `MAX(number)+1` 算 run.number → insert runs (status=pending, trigger_type=push, trigger_data=JSONB)
- `api/internal/handler/webhook/github_test.go` (290 行) — **15/15 PASS**:happy path / 错签名 / 缺签名 / 缺 event header / ping / 非默认分支 / tag ref / 项目不存在 / 非数字 project_id / 无 secret 配置 / dev_secret 兜底 / 非 push event / repo_type 非 github / store DB 错误 / createRun 失败
- `api/cmd/api/main.go` 装配:`webhookh.NewGitHubHandler(NewGormRunStore(gdb), gh, env)` 挂到 `v1` (公开,不过 auth 中间件)
- handler 包覆盖率 53.6% (handler 业务全过,未覆盖的是 GormRunStore 那段 SQL — 需要真 PG 才能跑,等容器起来一并测)

**设计决策**:
- 不用 go-github SDK (T1.2.1 已说明)
- 不用 secrets 表(暂)— 把 webhook_secret 明文存 projects.config JSONB 字段,T1.2.4 加自动注册时再迁到 secrets 表加密
- `ping` event 直接 short-circuit 不走签名校验,确保 GitHub 注册时 timeout 不会失败
- 非默认分支 push 默认过滤(不建 run),M2 加项目级 branches 白名单

**踩坑**:
- 第一版 handler 直接持 `*gorm.DB`,测试只能起真 PG,改抽 `RunStore` 接口 + fake 实现后测试瞬秒
- `patch` 模式插入新内容时把整段重复写到了文件顶部(旧内容没删),改用 `write_file` 整文件重写
- 沙箱 cwd 漂移导致 `write_file` 相对路径不稳,所有 patch 用绝对路径 `/Users/jie/Documents/...` 才稳

## E1.5 实时日志 (4d)

### T1.5.1 Redis Stream 写入 (0.5d)
**描述**: 日志流式入 Redis
**步骤**:
- Key 设计: `logs:run:{run_id}:step:{step_id}`
- XADD 单条日志 (ts/stream/msg)
- 配置 MAXLEN ~10000 (避免无限增长)

**验收**: 跑一次 run,redis-cli XLEN 看到日志数

### T1.5.2 WebSocket 服务端 (1.5d)
**描述**: 前端订阅日志
**步骤**:
- gorilla/websocket 接入
- 端点: GET /api/v1/runs/:id/logs/stream?step=
- 鉴权 (token via query string)
- 后端 XREAD 阻塞拉取,逐条推给 ws
- 连接断开自动清理
- 心跳 ping/pong (30s)

**验收**: 浏览器 console 用 WebSocket API 能连上看到日志

---

### T1.5.3 日志归档到 MinIO (1d)
**描述**: run 结束后批量落 MinIO,Redis 释放
**步骤**:
- run 终态时触发归档任务
- 从 Redis 读全部日志 → 拼接成 .log.gz → 上传
- key: `logs/{run_id}/{step_id}.log.gz`
- steps 表更新 log_offset / log_size
- 归档成功后删 Redis key

**验收**: run 完成 1 分钟后,MinIO 里能下载完整日志,Redis 已清

### T1.5.4 历史日志 HTTP 拉取 (1d)
**描述**: 历史 run 看日志走 HTTP
**步骤**:
- GET /api/v1/runs/:id/logs?step=&offset=&limit=
- 实时日志(进行中)走 Redis,历史日志走 MinIO
- 支持范围拉取 (用于无限滚动)
- ANSI 颜色码保留

**验收**: 拉去 1 个月前的 run 日志能正常显示

## 风险

- **最容易卡的: WebSocket + 鉴权** — 浏览器原生 WS 不能加 header,需 query string token 或先 HTTP upgrade
- **Docker 拉镜像超时** — 国内网络问题,提前配镜像加速
- **日志高频写 Redis 性能** — 单 run 10MB/s 验证一次
- **整体 19d task ≈ 4w 含 1w 缓冲,够用但紧**
- **UI 技术债**: 当前实现与原型差距大, E1.7 是收债任务, 优先级低于功能闭环, 但越拖越难还(后端字段长出来后改 UI 比一次性对齐成本高)
