**验收**: 三种连接场景都通

**完成产物**:

## E6.3 ssh-deploy 内置 step (2d)

### T6.3.1 step 定义 (0.5d) ✅
**步骤**:
- inputs: hosts (host_group 或主机列表) / source / dest / before_script / after_script / restart_command
- outputs: success_hosts / failed_hosts

**验收**: schema 完整

**完成产物**:
- `api/pkg/builtin/ssh_deploy.go` — inputs: `hosts`([]string) / `user` / `port` / `password` / `private_key` / `source` / `dest` / `before_script` / `after_script` / `restart_command`
- 额外策略参数: `strategy` / `batch_size` / `interval` / `max_failures` / `max_concurrency`
- outputs: `success_hosts` + `failed_hosts`

---

### T6.3.2 rsync 实现 (1d) 🔄
**步骤**:
- 优先用主机本地 rsync (检测可用性)
- fallback 到 sftp
- 增量传输 (基于校验和)
- 排除规则 (.rsync-exclude)

**验收**: 二次部署只传变更文件

**当前状态**:
- 当前使用 SFTP `UploadFile` / `UploadDir` 全量传输
- rsync 增量传输依赖远程主机预装 rsync, 且需通过 SSH exec 调用 `rsync --server`
- 作为优化项留待后续迭代 (当前全量传输在多数场景够用)

---

### T6.3.3 生命周期钩子 (0.5d) ✅
**步骤**:
- before_script (部署前在远程跑)
- after_script (部署后)
- restart_command (默认 `systemctl restart $service`)
- 失败立即停 (本主机)

**验收**: 三阶段顺序执行

**完成产物**:
- `SSHDeployStep.deployHost` 内顺序: snapshot → upload → before_script → restart_command → after_script
- 任一阶段失败立即返回 error, 该主机标记为失败, 不再继续后续阶段
- 失败触发整批回滚 (恢复已部署主机的 snapshot)

---

## E6.4 滚动并发控制 (2d)

### T6.4.1 并发执行框架 (1d)
**步骤**:
- 主机列表分批 (默认并发 5)
- 每批失败超过阈值停止 (max_failures)
- 进度实时上报

**验收**: 10 台主机 2 台失败,余下停止

---

### T6.4.2 部署策略配置 (0.5d)
**步骤**:
- DSL: deploy.strategy = rolling | parallel | serial
- rolling: 批次大小 / 批间间隔 / 失败阈值
- 健康检查 hook (跑完一批 curl /health)

**验收**: 三策略可切换

---

### T6.4.3 失败回滚 (0.5d)
**步骤**:
- 部署前 snapshot (备份旧目录)
- 失败时执行 restore (恢复 + 重启)
- 部分主机回滚 (已部署的)

**验收**: 故意一台失败,该台自动恢复

## 风险

- **SSH 密钥分发** — 用户体验差,提前考虑 helios CLI 一键分发
- **多主机并发** — goroutine 泄露风险,严格 wait group
- **rsync 在 Windows 主机不可用** — 文档明确不支持 Windows
- **总计 9.5d ≈ 2w,无缓冲**
